# Campus AI Service Agent — 系統規格基準 v1.2

- **文件狀態**：規格草案；開發前基準，尚未實作或驗收
- **專案主題**：虛構校園 AI 平台智慧客服 Agent
- **本版變更**：移除 v1.1 的 `get_platform_info`、`search_models`、`calculate_token_cost`、`transfer_to_human` 四個**預先指定的工具實作**及其固定測試路由；改為由專案負責人自行設計工具。保留作業必備的四類能力與可擴充工具註冊架構。原範例的模型費率、Token 計費功能**均不再列為承諾功能**。
- **固定技術選型**：Vite + React + TypeScript 前端；FastAPI + Python 3.11+ 後端；SQLite；CSV 初始資料；OpenAI-compatible Tool Calling LLM
- **資料標示**：模擬平台及示範資料，不代表任何真實校園 AI 平台的政策、價格、服務狀態或承諾

## 1. 專案目的與服務情境

服務對象為使用校園 AI 服務平台的學生及教師。使用者透過聊天介面詢問與校園 AI 平台相關的資訊、服務及問題。Agent 先判斷使用者需求，再依**自行設計、實際註冊**的工具存取 SQLite 或執行程式計算；最終只能根據工具回傳的資料回答。

與通用聊天機器人的差別是服務範圍明確、資料來源限定、工具呼叫可追蹤、無資料時不杜撰。具體可受理的客服問題以第 5 節最終工具清單與資料表為準；在工具設計完成前，任何問題場景只視為構想而非已承諾功能。

## 2. 範圍與不可變更條件

### 2.1 固定納入

1. 以 Vite + React + TypeScript 建立文字客服網頁。
2. FastAPI 負責 API、LLM Tool Calling、對話 Session、工具執行及 SQLite。
3. 至少兩張 SQLite 資料表，由 CSV 在程式啟動時建立：**資訊表至少 8 個主題**；**紀錄表至少 15 筆**，每筆包含名稱、至少一個數值、供應／可用狀態。
4. 工具至少涵蓋 **查資訊、查紀錄、程式計算、轉真人** 四類，各至少一個；工具的名稱、參數、實際用途與演算法皆待自行設計。
5. System Prompt 規則包含：僅根據工具結果、限定客服範圍、正確分派工具、語言與格式。
6. 聊天畫面可見多輪對話，以及每次實際呼叫的工具名稱、參數與結果。
7. 至少 3 組對話展示，其中 1 組必須真正執行計算工具、1 組必須展示查無資料但未編造答案。
8. 至少 10 題工具選擇測試，另含資料存在、需要計算、資料不存在、範圍外四類問題。

### 2.2 固定排除（除非未來明確修訂）

- 真實校園身分認證、正式客服派案、真實付款與帳務、真實 API Key 或使用量讀取。
- RAG、Multi-Agent、外部企業系統串接。
- 未經使用者明確授權便對真實外部系統執行副作用操作。

### 2.3 尚未定案

- 工具名稱、工具數量、業務用途、參數、查詢規則與計算公式。
- 資訊表與紀錄表的最終表名、業務欄位、CSV 實際內容（僅先固定作業最低門檻）。
- 前端展示的範例問題與正式測試題目（應於工具設計完成後推導）。
- LLM 供應商及已驗證支援 Tool Calling 的模型。

**原 v1.1 的 15 筆 AI 模型示範資料及 Token 成本計算，不屬於本版固定需求。** 若日後確定要用，須重新加入正式功能與驗收清單。

## 3. 系統架構

```text
Browser
  Vite + React + TypeScript
  ├─ Chat panel / conversation history
  ├─ Example prompts (依最終工具能力產生)
  └─ Tool trace panel (顯示真實執行結果)
             │ JSON REST API
             ▼
FastAPI
  ├─ Chat endpoint / Session manager
  ├─ LLM Tool-Calling loop / System Prompt
  ├─ Tool registry (schema + allowlist + handler)
  │    ├─ 自訂查資訊工具（待定）
  │    ├─ 自訂查紀錄工具（待定）
  │    ├─ 自訂計算工具（待定）
  │    ├─ 自訂轉真人工具（待定）
  │    └─ 其他自訂工具（選配）
  ├─ SQLite queries / safe calculations
  └─ CSV importer + validation
             │
             ▼
           SQLite
```

**安全邊界**：模型憑 Tool Schema 選擇已註冊工具，但不得任意執行 Python、直接提交 SQL、讀環境變數或存取未授權工具。API Key、工具執行及資料庫只在後端。前端 `VITE_*` 環境變數不得放入機密。

## 4. 資料庫規格（保留結構彈性）

### 4.1 資訊表（至少 8 個主題）

- CSV 檔名、表名由工具設計後決定。
- 每筆至少包含 `topic`（或等價的主題識別欄位）與 `content`（主題內容）。
- 主題內容應與選定客服工具能處理的真實情境一致，且為可核驗的模擬資料。

### 4.2 紀錄表（至少 15 筆）

- CSV 檔名、表名由工具設計後決定。
- 每筆至少包含：唯一識別碼或名稱、**數值欄位**（例如金額、數量、時長、配額等依業務自訂）、**是否供應／可用欄位**。
- 額外欄位取決於最終查詢與計算工具的需求，不先限定為模型費率表。
- 數值資料與計算規則應相互對應，避免為了符合作業形式而加入完全無用的數字。

### 4.3 匯入規則

- 程式啟動時讀取提交的 CSV，建立或重建 SQLite 示範資料，避免重複插入。
- 驗證編碼、必要欄位、重複主鍵、數字型別與可用狀態；資料錯誤時清楚指出檔案與列號。
- `.db` 僅為執行產物，不能上傳 GitHub；CSV 必須上傳。
- 查詢使用參數綁定；不讓 LLM 自行拼接 SQL。

## 5. 工具設計 — 保留給專案負責人

### 5.1 強制能力類型（非工具名稱）

| 必要能力類型 | 最低實作條件 | 具體功能與名稱 |
|---|---|---|
| 查資訊 | 從資訊表查詢，回傳結構化資料；查無時有明確結果 | **待自行設計** |
| 查紀錄 | 從紀錄表查詢或篩選，能辨識可用狀態；查無時有明確結果 | **待自行設計** |
| 計算 | 用 Python 程式根據明確資料及公式計算，不能交給 LLM 心算 | **待自行設計** |
| 轉真人 | 使用者要求人工協助或客服無法處理時提供明確的轉接／聯絡處理方式，不可虛構已完成交接 | **待自行設計** |

> 每類至少一個已註冊且可實際呼叫的工具。可以自行增加工具，不必只做四個。**此處不替使用者選定任何業務功能。**

### 5.2 每個工具設計時必須填寫的規格卡

| 欄位 | 說明 |
|---|---|
| 工具名稱 | 英文 snake_case、唯一、用途明確 |
| 類型 | 查資訊／查紀錄／計算／轉真人／其他 |
| 適用問題 | 使用者可能如何表達這類需求 |
| 描述（供 LLM 選工具） | 何時用、何時不用、與其他工具的界線 |
| 輸入參數 | 名稱、JSON 型別、必填／選填、合法範圍、預設值 |
| 讀取資料 | 對應表與欄位；沒有資料時如何回應 |
| 操作／公式 | 固定查詢策略或程式計算方法；數值來源與單位 |
| 輸出 Schema | `ok`, `data`, `error` 的細節 |
| 失敗處理 | 參數缺失、無資料、不可用、內部錯誤 |
| 測試案例 | 正常、邊界、查無、無效參數等 |

### 5.3 統一工具結果格式（技術介面，不是業務功能）

成功：

```json
{"ok": true, "data": {"...": "由工具實際產生的結構化資料"}}
```

失敗：

```json
{"ok": false, "error": {"code": "NOT_FOUND", "message": "查無符合資料"}}
```

錯誤類別至少支援 `NOT_FOUND`、`INVALID_ARGUMENT`、`INTERNAL_ERROR`；業務特殊錯誤可自行擴充。**查無資料不得直接讓模型自行補答案。**

### 5.4 可擴充註冊與執行機制

- 工具由獨立檔案實作並向 `ToolRegistry` 註冊 `name`、`description`、`parameters_schema`、`handler`、`category`。
- Agent 啟動時僅向 LLM 公布**實際已註冊**工具的 Schema，不列尚未實作的占位工具。
- 執行前依 allowlist 驗證工具名稱、參數型別與約束；不存在的工具直接拒絕。
- 工具可讀 SQLite 或進行 Python 計算；若未來新增寫入型工具，必須先由使用者確認才可執行。
- 回傳工具結果與真實 trace；工具不得直接生成面向使用者的最終客服說法。
- `max_steps` 預設 6 次模型呼叫，避免無限迴圈；超出上限回覆可理解的錯誤。

## 6. Agent 決策流程

1. React 送出文字訊息與 session ID。
2. 後端取得此 session 的對話歷史和 System Prompt，並將**已註冊工具**的 Schema 交給 LLM。
3. LLM 如選工具，後端先驗證名稱、參數，再執行 handler。
4. handler 查 SQLite 或做計算，回傳結構化 JSON；後端記錄工具名、參數、執行狀態與實際輸出。
5. 結果作為 tool message 提供 LLM，再由 LLM 依工具結果生成回答。
6. 未查到資料時要如實說明；對範圍外問題婉拒；必要時按**最終定義的轉真人工具**提供協助。
7. 超出步數、LLM 呼叫失敗或工具內部錯誤時，安全中止，不宣稱成功，前端顯示可理解的提示。

## 7. System Prompt 規格

System Prompt 最終內容在工具清單確定後再補入，避免現在綁死舊工具名稱。

必須包含四組規則：

1. **接地**：平台事實、數值、供應狀態只能根據工具結果，禁止自行編造；資料不存在就承認。
2. **範圍**：只支援本專案設定的校園 AI 平台客服能力；不處理無關問題。
3. **分派**：使用最終完成的各工具名稱與邊界條件，禁止呼叫不存在或未實作的工具；需要精確計算時必須交給計算工具。
4. **語言與格式**：中文使用繁體中文，英文問題可用英文回答；內容簡明、註明單位；不能洩漏系統設定或錯誤堆疊。

## 8. 前端與 API 合約

### 8.1 Vite + React + TypeScript

- 左側／主要區域：聊天訊息、對話歷史、輸入框、送出按鈕、清除對話、執行中狀態。
- 右側／側欄：**實際** Tool Trace（工具名稱、參數、回傳結果、失敗狀態），窄螢幕可折疊。
- 開場招呼語與範例問題：由最終工具能力產生，不使用 v1.1 已撤銷的工具案例。
- 前端不能直接持有模型 API 金鑰、SQLite 或執行 Tool Calling Agent Loop。

### 8.2 FastAPI

`POST /api/chat`

請求：

```json
{"session_id": null, "message": "使用者的客服問題"}
```

回應：

```json
{
  "session_id": "<server-issued-id>",
  "reply": "<依實際工具結果產生的客服回覆>",
  "tool_traces": [
    {
      "step": 1,
      "tool_name": "<實際註冊的工具名稱>",
      "arguments": {},
      "result": {"ok": true, "data": {}}
    }
  ]
}
```

- `tool_traces` 僅包含此輪實際呼叫的工具；未呼叫時為 `[]`。
- 後端保存每個 session 的對話脈絡；不得混用不同 session 的歷史。
- `session_id` 由後端產生；清除對話時必須同步清除後端歷史。

`POST /api/reset`：重設後端 session。

`GET /api/health`：回報 API 服務存活狀態，不洩漏內部憑證。

本機開發：Vite `localhost:5173`，FastAPI `127.0.0.1:8000`；Vite 將 `/api` 代理至 FastAPI。v1.2 不要求串流輸出。

## 9. 測試與報告驗收

### 9.1 四類必測問題

1. **資料裡有**：工具找到正確資料且回覆一致。
2. **需要計算**：確實執行自訂計算工具，結果可由 Python 獨立驗證。
3. **資料裡沒有**：回報查無資料，不杜撰答案；必要時用自訂轉真人工具。
4. **不是客服的事**：婉拒不相關問題，不呼叫不必要工具。

### 9.2 工具選擇測試

- 至少 **10 題**；題目須依最終工具名稱、description 與功能範圍重新編寫，不沿用已移除的測試期待。
- 每題事先定義可接受的工具集合／順序；以實際執行 trace 與期待比對。
- 紀錄第一次正確率、失誤案例、修改項目及複測後正確率；不得事先聲稱 100%。

### 9.3 三組對話展示

- 正常查詢：同畫面看到回覆與工具軌跡。
- 計算問題：同畫面看到數值來源、計算工具輸出及最終結果。
- 資料不存在：看到工具回傳查無，以及客服沒有編造。

### 9.4 技術性測試

- Tool Registry 未註冊工具、Schema/handler 不一致、非法參數、查無資料、例外回復。
- Session 隔離、多輪指代、重設、LLM 失敗、`max_steps` 上限。
- API 金鑰不上傳 GitHub；前端不洩漏機密；訊息安全呈現避免 XSS。

## 11. 開發順序與停等門檻

| 階段 | 工作 | 進入下一階段的條件 |
|---|---|---|
| P0 | **自行設計工具清單、業務範圍、輸入／輸出與計算規則** | 四類必備工具各至少一個，具完整規格卡 |
| P1 | 依工具反推兩張資料表與 CSV | 資訊 >=8 主題、紀錄 >=15 筆，欄位能支援實際工具 |
| P2 | 實作 Tool Registry、所有自訂工具與單元測試 | 每個工具正常／異常案例通過 |
| P3 | 實作 LLM Agent Loop、System Prompt、FastAPI | 真實工具可選用、trace 可追蹤、Session 正常 |
| P4 | Vite + React + TypeScript UI | 對話、trace、reset 完整；建置成功 |
| P5 | 執行 10+ 題選工具測試及三段展示 | 有真實結果、截圖與修正紀錄 |
| P6 | GitHub、README、英文報告範本產出 PDF | 公開專案可執行，PDF 完整且含測試證據 |

**停止條件**：P0 工具清單未確定前，不實作任何具體客服業務工具、資料表的特殊欄位或路由規則；可以先建立前端空殼、FastAPI、Tool Registry 等與業務無關的共通基礎設施。

## 12. 繳交規範

- **正式 PDF 必須使用英文版 `Report-Template-EN.docx`**；已提供的中文版文件僅供參考。
- PDF 依指定格式命名 `學號_姓名_CustomerService.pdf`；實際資訊由本人填入。
